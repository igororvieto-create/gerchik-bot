# Бриф для ревью gerchik-bot

Этот файл — обязательное чтение перед любой проверкой кода (человеком или
агентом). Он даёт эталонные значения, связи между параметрами и роли, чтобы
проверяющие не дублировали друг друга и не выдавали ложных находок.

---

## 0-А. Обязательная дисциплина проверки (добавлено после разбора ошибок)

Эти правила появились из РЕАЛЬНЫХ ошибок агентов и автора правок в этом
проекте. Каждое сформулировано так, чтобы конкретную ошибку нельзя было
повторить.

1. **Сначала запусти тесты: `python -m pytest tests/ -q`.** В `tests/`
   зафиксированы все ранее найденные баги. Если тест уже падает — это и
   есть находка, и искать её вручную не нужно. Если твоя находка не
   ломает ни один тест, добавь тест, который её ловит: находка без теста
   вернётся через два коммита.

2. **Считай эффект в ОБЕ стороны.** Главная ошибка сессии: предложение
   «переносить стоп в безубыток даёт +0.146R» посчитало убытки, ставшие
   безубытком, и НЕ посчитало победы, которые перенос убивает (путь
   0 → +1R → откат → +2R). Честная симуляция показала, что эффекта нет.
   Прежде чем называть число выигрышем, перечисли, что этот же механизм
   ЗАБИРАЕТ.

3. **Сверяйся с теорией, а не только с симуляцией.** Для процесса без
   сноса никакое правило выхода не создаёт матожидания (теорема об
   остановке). Любая находка вида «поменяем правило выхода и получим
   плюс без улучшения отбора» противоречит этому и почти наверняка
   ошибочна. То же про соотношение 1R/2R: оно даёт ровно 33.3% побед при
   НУЛЕВОМ преимуществе — «винрейт 33%» не значит «почти работает», это
   значит «преимущество не обнаружено».

4. **Проверь, не артефакт ли это твоей модели.** Симуляция с хай/лоу,
   нарисованными как независимый шум, завышает вероятность касания
   близкого стопа и даёт ложный результат. Генерируй путь поминутно и
   собирай из него честные экстремумы бара.

5. **Отличай «измеряемое» от «предполагаемого».** Если гипотезу можно
   проверить по уже собранным колонкам (`score, direction, signal_type,
   sl_pct, atr_pct, headroom, mfe_r, outcome`) — проверь по ним, а не по
   модели. Если нельзя — предложи инструментовку, а не вывод.

6. **Размер выборки.** 15 исходов не отличают прибыльную стратегию от
   убыточной: 95% интервал для 5W/10L — от 15% до 58%. Чтобы доказать
   винрейт 45% против безубытка, нужно ≈80 исходов; при слабом
   преимуществе (38%) — около 400. Не делай выводов о параметрах по
   десяткам наблюдений.

7. **Матожидание, а не процент побед.** С появлением исхода BE винрейт
   перестал быть достаточной метрикой. Решение принимается по `ev_r`.

## 0. Правила, экономящие время

1. **Сначала `git log --oneline -5`.** Код мог измениться после того, как
   тебе поставили задачу. Находка по устаревшей версии — потерянное время.
   Всегда цитируй актуальный код, а не тот, что ожидал увидеть.
2. **Проверяй утверждение до того, как его писать.** Если пишешь «выражение
   парсится не так» — проверь через `python3 -c "import ast; ..."`. Если
   «этот код недостижим» — приведи цепочку условий.
3. **Находка без конкретного сценария отказа — не находка.** Нужны входные
   данные → неверный результат. «Может быть опасно» не принимается.
4. **Отличай баг от компромисса.** Многие пороги подобраны намеренно и
   описаны в разделе 2. Прежде чем звать что-то багом, посмотри там причину.

## 1. Инварианты (нарушать нельзя никогда)

Проверяются в `core/config.py::_clamp` и в `/api/settings`. Если находишь
путь, который их обходит, — это находка максимального приоритета.

| Инвариант | Где enforced | Что искать |
|---|---|---|
| Риск на сделку 1–3% | `_clamp` + API 0.1–3.0 | любой расчёт размера позиции мимо `RISK_PER_TRADE` |
| Плечо ≤ 5x | `_clamp` + API 1–5 | прямая подстановка плеча из env/тела запроса |
| SL обязателен ДО входа | `enter_trade` + монитор | путь, где позиция живёт без подтверждённого стопа |
| Не торговать листинги/спайки | `MIN_LISTING_AGE_DAYS`, `MAX_LAST_CANDLE_ATR` | обход гейтов, освобождения от них |

**Рецидивирующие баги — проверять в каждом ревью:**

- **№1: SL как чарт-маркер.** `retCode == 0` НЕ доказывает, что стоп на
  бирже. Требуется чтение живой позиции. Частный случай, уже случавшийся
  дважды: `set_trading_stop(sl=0)` отправляет запрос без поля `stopLoss`,
  биржа отвечает успехом — «стоп восстановлен», которого нет.
- **№2: score и direction врозь.** Любой фактор, добавляющий очки, обязан
  либо подтверждать направление, либо не давать очков. Ищи слагаемое score,
  которое начисляется независимо от `direction`. Уже ловили трижды: VSA,
  уровень, затем стакан+фандинг через `abs()`. Признак — `abs(x)` в
  `_score_signal`; сейчас все направленные компоненты берут `direction`.
- **№3: пороги, совпавшие с рыночной константой.** `0.01` в коде — это
  ровно нейтральная ставка фандинга Bybit (`0.0001 × 100`). Порог, стоящий
  на ней, срабатывает почти всегда: так голос фандинга задавал направление
  2/3 сделок, а префильтр мёртвых тикеров не фильтровал ничего. Проверяй
  каждую числовую константу на совпадение с типичным рыночным значением.
- **№4: `retCode == 0` у `/v5/order/create`** означает «ордер принят», а не
  «позиция закрыта». IOC reduceOnly заливается частично. Закрытие обязано
  идти через `trader.close_and_verify`, а не голым `close_position`.
- **№5: функция БД, возвращающая пустое вместо исключения.** `[]` от
  `get_open_trades` читается как «своих сделок нет» → позиции бота получают
  ярлык MANUAL и теряют защиту; `0.0` от `get_realized_pnl_since` обнуляет
  дневной предохранитель. Обе теперь БРОСАЮТ — сохраняй это свойство.

## 2. Эталонные параметры и связи

Значения ниже — рабочие дефолты. Отклонение само по себе не баг (всё
настраивается через env), но **нарушение связей между ними — баг**.

### Торговля

| Параметр | Знач. | Почему именно так |
|---|---|---|
| `RISK_PER_TRADE` | 1.0 | инвариант 1–3% |
| `LEVERAGE` | 5 | инвариант ≤5x |
| `MAX_POSITIONS` | 3 | 3 × 1% = 3% одновременного риска |
| `MAX_SAME_DIRECTION` | 2 | 3 лонга в коррелирующих альтах = одна ставка втройне |
| `MAX_MARGIN_PCT` | 10 | потолок маржи от баланса |
| `TRADE_MIN_SCORE` | 45 | **не 60**: шкала дискретна, при ΔOI<5% потолок 59 |
| `DAILY_LOSS_LIMIT_PCT` | 6.0 | 6 стопов при риске 1%, 2 при риске 3% |
| `ABORT_ON_LEVERAGE_FAIL` | true | сайзинг считался под известное плечо |

**Связи (проверять!):**
- `RISK_PER_TRADE × MAX_POSITIONS ≤ DAILY_LOSS_LIMIT_PCT` — иначе один
  «полный» набор позиций пробивает дневной лимит разом.
- `TRADE_MIN_SCORE ≥ MIN_SCORE` — торговый порог не может быть ниже порога
  показа.
- `TRADE_MIN_SCORE` должен быть **достижим**: посчитай максимум `_score_signal`
  для реалистичного сетапа. Если порог берут только экстремальные значения
  одного компонента — селекция вырождается (так и получилось 1W/14L).

### Отбор сигналов

| Параметр | Знач. | Роль |
|---|---|---|
| `MIN_SCORE` | 30 | порог показа и попадания в форвард-тест |
| `OI_CHANGE_THRESHOLD` | 2.0 | граница классификации ACCUMULATION/SQUEEZE |
| `VOL_SPIKE_MULT` | 1.5 | ×1.5 → порог VOLUME_SPIKE |
| `FUNDING_EXTREME` | 0.03 | % |
| `PRICE_CHANGE_MIN` | 0.3 | префильтр мёртвых тикеров |
| `OB_IMBALANCE_THRESHOLD` | 0.10 | перекос стакана для голоса |
| `MIN_VOL_24H` | 2 000 000 | ликвидность |
| `SIGNAL_COOLDOWN_MIN` | 60 | пауза по символу |

### Стратегия (Герчик)

| Параметр | Знач. | Роль и связи |
|---|---|---|
| `MIN_RR` | 1.5 | порог ПОКАЗА: запас до противоположного уровня |
| `MIN_TRADE_HEADROOM_R` | 2.0 | порог ТОРГОВЛИ, читается в `enter_trade` |
| `KEY_LEVEL_LOOKBACK` | 20 | окно поиска пивотов |
| `KEY_LEVEL_WING` | 2 | плечи фрактала |
| `KEY_LEVEL_ATR_MULT` | 1.2 | макс. удаление входа от уровня (**только не-VSA**) |
| `LEVEL_NOISE_ATR` | 0.5 | пивоты ближе — рыночный шум, не уровень |
| `MAX_SL_ATR` | 3.5 | потолок ширины стопа |
| `MAX_LAST_CANDLE_ATR` | 2.0 | анти-спайк (**только не-VSA**) |
| `REVERSAL_MAX_DRIFT_ATR` | 1.0 | разворот должен входить рядом с сетапом |
| `REQUIRE_MTF_ALIGN` | true | тренды 1h/4h (**только не-VSA**) |
| `MTF_TREND_LOOKBACK` | 6 | баров для оценки тренда |
| `MIN_LISTING_AGE_DAYS` | 14 | инвариант «не торговать листинги» |

**Ключевая геометрия — считать при каждом изменении порогов:**

```
sl_dist ≈ KEY_LEVEL_ATR_MULT + 0.25 (буфер) = 1.45 ATR
нужно до цели ≥ sl_dist × MIN_RR = 2.18 ATR
```

Если поднять `KEY_LEVEL_ATR_MULT` или `MIN_RR`, требуемый чистый ход растёт
квадратично — и сетапы перестают проходить. Это уже приводило к нулевому
потоку сигналов.

**Освобождения VSA — источник половины багов.** `is_vsa_reversal` снимает
анти-спайк, MTF и гейт близости. Проверяй:
- освобождение даётся только при `sig_type.startswith("VSA_")`, а не по
  факту обнаружения паттерна;
- `VSA_*` требует `vsa_bias != NEUTRAL`;
- для разворота есть **свой** ограничитель (`REVERSAL_MAX_DRIFT_ATR`),
  иначе он входит вдогонку с другой стороны.

### Сканирование и хранение

| Параметр | Знач. | Связь |
|---|---|---|
| `SCAN_INTERVAL_MIN` | 4 | цикл скана должен укладываться в интервал |
| `SCAN_BATCH_SIZE` / `SCAN_BATCH_DELAY` | 10 / 0.5 | rate-limit Bybit |
| `TOP_N_PAIRS` | 100 | ×4 запроса на символ |
| `MAX_SIGNALS_DB` | 5000 | ≥ 8 суток потока, иначе режет 7-дневную статистику |
| `SIGNAL_TTL_HOURS` | 24 | фактическое хранение `max(TTL, 192)` — оценщику нужно 48ч |

## 3. Роли в группе (не дублировать друг друга)

Каждый агент читает свои файлы и **не лезет в чужие**, кроме как для сверки
контрактов.

| Роль | Файлы | Фокус |
|---|---|---|
| **A. Стратегия** | `strategy/scanner.py`, `evaluator.py` | математика скоринга, геометрия уровней, достижимость порогов, освобождения VSA, индексация свечей (`[-1]` — незакрытая, `[-2]` — последняя закрытая) |
| **B. Деньги** | `strategy/trader.py`, `exchange/bybit.py` | сайзинг, подтверждение SL/TP на бирже, гонки со слотами, дневной предохранитель, идемпотентность ордеров |
| **C. Данные** | `core/db.py`, `core/state.py`, `main.py`, `core/config.py` | миграции, индексы, дедуп, планировщик, завершение работы, разбор env |
| **D. Интерфейс** | `static/index.html`, `api/routes.py` | контракты API↔фронтенд, XSS, гонки WS/polling, границы ползунков = границы валидации |

**Обязательная сверка на стыках** (иначе баги проваливаются между ролями):

- A↔B: поля `Signal`, которые читает `enter_trade` (`score`, `direction`,
  `entry`, `sl`, `tp2`, `sl_pct`).
- B↔C: `Position` ↔ таблица `trades`; что происходит при рестарте с
  открытой позицией.
- C↔D: имена полей в ответах API ↔ то, что читает JS.
- Все: параметр, добавленный в `config.py`, должен где-то **читаться**;
  мёртвый параметр — находка.

## 4. Быстрые проверки перед выводами

```bash
# все cfg.* существуют и используются
python3 - <<'EOF'
import re, os
used=set()
for r,_,fs in os.walk('.'):
    if '.git' in r or '__pycache__' in r: continue
    for f in fs:
        if f.endswith('.py'):
            used |= set(re.findall(r'\bcfg\.([A-Z_][A-Z0-9_]*)\b',
                        open(os.path.join(r,f),encoding='utf-8').read()))
from core.config import cfg
print("нет в конфиге:", [u for u in used if not hasattr(cfg,u)])
print("мёртвые:", [a for a in dir(cfg) if a.isupper() and a not in used])
EOF

# достижим ли торговый порог
python3 -c "
import strategy.scanner as s
from core.config import cfg
for oi in (2,4,6,10):
    print(oi, s._score_signal(oi,2.5,0.02,0.15,2.,vsa_type='NEUTRAL',level_dist_atr=0.3)[0], '/', cfg.TRADE_MIN_SCORE)"
```

**Типичные ложные срабатывания:**

- «Сигналов не будет вовсе» — сначала прогони сквозной тест с фейковым
  клиентом на реалистичных данных (откат к уровню, климакс после падения).
  Монотонный ряд без откатов пивотов не даёт вовсе — это артефакт данных.
- «Код недостижим» — проверь, не меняется ли условие в рантайме через
  `/api/settings`.
- «Гонка» — убедись, что между операциями действительно есть `await`.
